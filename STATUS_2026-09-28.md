## 1. Your document was right, and where we disagreed we were wrong

All three of your §0 claims were verified independently, by tracing the call
graph rather than trusting either reading:

**The pass.** `render_world_face_list` (0x2ad21) has three callers, all in
`render_world.c` (117, 155, 187) — the real world render.
`render_world_face_list_subpass` (0x28dbe) has exactly one caller,
`renderer.c:9565`, inside the function that sets a one-pixel view window. Every
flat rule we had written came from the **cursor-pick pass**.

**The mirrors.** Visible pass, `renderer.c:9229` / `:9249`:

```c
ceiling: fill_mode = 0x38 | ((sector[0x17] & 0x0c) >> 1);
floor:   fill_mode = 0xb8 | ((sector[0x17] & 0x03) << 1);
```

Sector bits are ORed in, exactly as you have it. We had deleted the (correct)
mirror code on the strength of the pick pass, and have restored it.

**The driver.** Dispatch at `renderer.c:13314` tests `& 0x20` before `& 0x200`.
The visible fill word is `0x38`/`0xb8`, both with `0x20` set, so world flats go
to `draw_scaled_sprite_spans` — which is where `renderer.c:3357` reads the scale.
Flats do use the scale. **Per-plane UV engine work is stopped**; it was scoped on
the wrong finding and nothing was built.

## 2. Two source findings of our own, both verified

**The 256×256 exception is 256×256 *and opaque*.** `renderer.c:3367` branches on
`(width == height && (uint8_t)width == 0)`, then on `span_textured_mode_flag`,
which selects the opaque loop `0x3a220` versus the translucent `0x3a100`
(`renderer.c:3341`). That flag is **bit 26 of the texture block's +8 dword**
(`renderer.c:13281`) — a per-image property, so the loader can know it
statically. Your §3.1 exception is right and now has a mechanism.

**`roth_runtime.cpp:1997` is worse than the audit said.** It duplicates the
loader's flat scale but drops the mirrors entirely, so a platform changes
appearance the moment it moves. That is defect #4's second half, and it is a
concrete bug rather than a tidiness complaint.

## 3. The one hard measurement we have

An instrumented ROTH.C run, filtered to the visible pass (256 rows accepted,
312,694 pick-pass rows rejected), with texture sizes read **after** resolution:

| surface | s | texture | ROTH (`2^s`, 256-opaque `2^(s-1)`) | REMAROTH (`2^s·2`) | error |
|---|---|---|---|---|---|
| floor | 1 | 32×32 | **2** | 4 | 2× too coarse |
| floor | 1 | 64×64 | **2** | 4 | 2× too coarse |
| ceiling | 1 | 32×16 | **2** | 4 | 2× too coarse |
| ceiling | 2 | 256×256 | **2** (via the exception) | 8 | 4× too coarse |

Every surface lands on **2 world units per texel**, including the 256×256 one,
which only gets there *because* of the `2^(s-1)` exception. A wrong exception
would have produced 4 and broken the agreement. That is a real check on your
rule, not a restatement of it.

It also reproduces defect #2's prediction exactly: "2× (or 4×) too coarse", with
the 4× falling precisely on the 256×256 ceiling.

## 4. Sky / colour key — your §3.6 data check, answered

Static audit over all 44 retail maps (`tools/oraclelog/skyaudit.cpp`):

```
key floors            263
key ceilings        5,945
key flats           6,208   <- exactly reproduces the old "sky flat" count
key wall pieces    33,255
EDGE_MAP faces      4,304
```

Two results:

- **The colour key and our "sky marker" are the same set** (263 + 5,945 = 6,208,
  matching exactly). `SkyMarkerIndex()` — DAS header +0x22 — *is* the colour key.
  Same field, wrong name on our side.
- **33,255 key *wall* pieces**, five times the flat count, none of which we ever
  treated as sky. There is no reading of "this is sky" that survives 33,255 sky
  walls. "Draw nothing" is the only rule that fits all three surface kinds, which
  agrees with your code trace from an independent direction.

**Key ceilings with no EDGE_MAP anywhere in the map** — the exception list you
asked for. Six maps, 33 ceilings:

```
MAS3        2        MAUSO1EB    2
MAS4        3        OPTEMP1     1
MAS7       24        SALVAT      1
```

So key ceiling → engine sky is correct for 38 of 44 maps and harmless in them;
those 33 are where it would show sky with nothing to justify it.

(We also report 3,965 of 5,945 key ceilings having no EDGE_MAP face in their
*own* sector, but we do not think that number means anything — a sky band from a
neighbouring sector is still visible through a key ceiling, so adjacency is the
wrong containment test.)

## 6. What is blocked, and the decision we want

We built `rothdiff`, an agent-facing per-pixel diff: for a camera pose, both
engines record which surface they drew at every pixel and out of which texture,
and the output is a match percentage with mismatches grouped by cause.

**The ROTH.C half works.** All ten camera spots capture in a single headless run,
loading a save automatically (F10, scancode 0x44, read out of the game's own
keymap table at 0x7093d).

**The REMAROTH half does not.** It raycasts one ray per pixel through the
engine's `Trace()`. It launches fullscreen, wedges on load, and has cost the
whole evening. 640×480 is 307,200 traces per shot and something in that loop is
wrong beyond mere slowness.

**Our proposal: drop the screen capture for now.** The live question — is the
carpet the right size, mirrored, shifted — needs no rendering. We already have
both halves offline:

- `roth_surface::FlatTexel` — what ROTH.C samples at a world point
- `roth_surface::EngineTexel` — what GZDoom samples given the loader's values
- the loader's own data, which already produces a **zero-diff** static
  comparison against the oracle

So the test is: every sector in all 44 maps, sample points, compare. Seconds to
run, no window, and it catches exactly the class of bug we are chasing — scale,
shift, mirror, sign. It does **not** catch occlusion, projection, eye height or
FOV, which are real but are not why the carpet is wrong.

**Question for you: agreed to go offline-only for flats, and revisit the
per-pixel screen diff after the flats pass?**

## 7. Two corrections to your document

**§3.7 pixel stretch will not fix room height on our renderer.** We set
`pixelratio = 1.0` and it is correct for Realms, but we traced where the value is
consumed:

```
VREyeInfo::GetProjection(fov, aspectRatio, fovRatio)   hw_vrmodes.cpp:1350
    -> result.perspective(fovy, aspectRatio, zNear, zFar)
aspectRatio = r_viewwindow.WidescreenRatio              hw_entrypoint.cpp:718
WidescreenRatio = fullWidth / fullHeight                r_utility.cpp:335-339
```

No pixelstretch term. It is read only by the **software** renderer
(`r_viewport.cpp:164-174`), camera textures (`hw_entrypoint.cpp:709`), and the VR
transforms. So "the default 1.2 makes rooms ~20% taller" is true of the software
renderer and **not** of the path we run.

The open candidates for room height are therefore the other two in §3.7. One is
measurable now: ROTH's horizontal FOV is ~91.8°
(`focal = view width × 0x7C/256` → `tan(h/2) = 0.5/0.484375`), and **we set no
FOV at all**, so we inherit GZDoom's 90°. Nobody has closed that 2%.

**§3.1's two signs remain `[derived]`.** They are implemented so the test can
check them, and are tagged in both header and code with "do not cite this code as
evidence for them". Confirming them needs the oracle, not the encoding test.
